Technical Architecture · Deep Dive

How the Workflow
Actually Works

Three core mechanisms power everything: a shared state object that flows between agents, a LangGraph state machine that decides what runs next, and a PostgreSQL checkpointer that makes approval gates possible.

The Three Core Concepts

01

Shared State Object

A single Python dict that travels through the entire workflow. Every agent reads from it and writes back to it. This is how agents "talk" to each other — not directly, but through shared memory.

02

LangGraph State Machine

A directed graph where nodes are agent functions and edges are transitions. LangGraph decides which node runs next, handles branching (parallel agents), and supports interrupts (approval gates).

03

PostgreSQL Checkpointer

After every node completes, the full state is saved to PostgreSQL. This is what makes approval gates work — the graph can pause for hours, and resume exactly where it stopped.

The State Object — What Flows Between Agents

Every agent receives the full state and returns an updated version. Nothing is passed directly between agents.

Why shared state? The Architect agent doesn't call the PM agent. It reads state["requirements"]. The Backend agent reads state["architecture"] and state["db_schema"]. This makes every agent independently testable — just pass it a state dict.

How a Single Agent Node Works

Every agent follows the same pattern. Here's the PM Agent in full:

import time
from anthropic import Anthropic

client = Anthropic()

def run_pm_agent(state: WorkflowState) -> WorkflowState:
    start = time.time()

    # 1. Build prompt from current state
    system_prompt = """You are a senior product manager.
    Produce a structured requirements document.
    Return your output as a markdown document."""

    user_prompt = f"""Product Idea: {state['user_input']}

    Past project context (from memory):
    {state.get('past_decisions', 'None')}

    User preferences:
    {state.get('user_preferences', {})}

    Produce:
    - Functional requirements (numbered list)
    - User stories (As a... I want... So that...)
    - Acceptance criteria per story
    - Non-functional requirements
    - Explicitly out of scope items"""

    # 2. Call the Claude API
    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=4096,
        system=system_prompt,
        messages=[{"role": "user", "content": user_prompt}]
    )

    # 3. Track metrics
    latency = time.time() - start
    cost = calculate_cost(response.usage, "claude-sonnet-4-6")

    # 4. Write output back to state — return full updated state
    return {
        **state,
        "requirements": response.content[0].text,
        "metrics": {
            **state.get("metrics", {}),
            "pm_agent": {
                "tokens_in":  response.usage.input_tokens,
                "tokens_out": response.usage.output_tokens,
                "cost_usd":   cost,
                "latency_s":  latency,
            }
        }
    }

The pattern is always: read from state → build prompt → call Claude → parse response → write output + metrics back to state. Every agent is a pure function that takes state in and returns updated state out.

The LangGraph State Machine

LangGraph wraps those agent functions into a directed graph. It decides what runs next, handles branching, and manages pauses.

from langgraph.graph import StateGraph, END
from langgraph.types import Send
from langgraph.checkpoint.postgres import PostgresSaver

# --- Build the graph ---
builder = StateGraph(WorkflowState)

# Register every node (agent function)
builder.add_node("pm_agent",       run_pm_agent)
builder.add_node("architect_agent", run_architect_agent)
builder.add_node("backend_agent",   run_backend_agent)
builder.add_node("frontend_agent",  run_frontend_agent)
builder.add_node("qa_agent",        run_qa_agent)
builder.add_node("join",            join_parallel_outputs)
builder.add_node("reviewer_agent",  run_reviewer_agent)

# Linear edges
builder.set_entry_point("pm_agent")
builder.add_edge("pm_agent",       "architect_agent")
builder.add_edge("architect_agent", "backend_agent")   # explained below

# Fan-out: after architect, dispatch 3 agents in parallel
def dispatch_parallel(state: WorkflowState):
    return [
        Send("backend_agent",  state),
        Send("frontend_agent", state),
        Send("qa_agent",       state),
    ]

builder.add_conditional_edges("architect_agent", dispatch_parallel)

# All three parallel agents converge at "join"
builder.add_edge("backend_agent",  "join")
builder.add_edge("frontend_agent", "join")
builder.add_edge("qa_agent",       "join")
builder.add_edge("join",            "reviewer_agent")
builder.add_edge("reviewer_agent",  END)

# Attach PostgreSQL checkpointer — saves state after every node
checkpointer = PostgresSaver(conn_string=DATABASE_URL)

# interrupt_before: pause the graph BEFORE these nodes, wait for resume
workflow = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["architect_agent", "backend_agent"]
    #                    ^ Gate 1                ^ Gate 2
)

How Approval Gates Work

This is the most important mechanism to understand. LangGraph's interrupt_before makes the graph pause mid-execution, save everything, and wait indefinitely until resumed via the API.

# --- Running the workflow (called by Celery worker) ---

def run_workflow(project_id: str, user_input: str):
    config = {"configurable": {"thread_id": project_id}}
    initial_state = {"project_id": project_id, "user_input": user_input}

    # Graph runs pm_agent, then PAUSES before architect_agent
    # State is saved to PostgreSQL. Function returns here.
    workflow.invoke(initial_state, config)

# --- FastAPI: user approves Gate 1 ---

@router.post("/projects/{project_id}/approve")
async def approve_gate(project_id: str, body: ApprovalBody):
    config = {"configurable": {"thread_id": project_id}}

    # Inject user feedback into the paused state
    workflow.update_state(config, {
        "gate1_approved": True,
        "gate1_feedback": body.feedback  # optional edits from user
    })

    # Queue resumption in Celery — graph picks up from the interrupt point
    resume_workflow.delay(project_id)
    return {"status": "resumed"}

# --- Celery task: resumes from checkpoint ---

@celery.task
def resume_workflow(project_id: str):
    config = {"configurable": {"thread_id": project_id}}
    # None means: resume from saved checkpoint, don't restart
    workflow.invoke(None, config)
    # Graph continues: architect_agent → pause at Gate 2 → ... → END

Key insight: The graph can sit paused for minutes, hours, or days. The state is in PostgreSQL. When the user approves, the Celery task picks up the exact same state object — with the PM agent's output already in it — and continues from the interrupt point. No data is lost, no agent re-runs.

How Parallel Execution Works

After Gate 2, three agents run at the same time. LangGraph's Send() dispatches them concurrently. The join node waits until all three have written back to state.

# dispatch_parallel() returns 3 Send() calls simultaneously
# LangGraph runs backend_agent, frontend_agent, qa_agent in parallel threads

def join_parallel_outputs(state: WorkflowState) -> WorkflowState:
    # By the time this runs, all three have written to state:
    # state["openapi_spec"]   ← from backend_agent
    # state["task_backlog"]   ← from backend_agent
    # state["frontend_spec"]  ← from frontend_agent
    # state["test_plan"]      ← from qa_agent

    # This node just validates all three are present before reviewer runs
    missing = [
        k for k in ["openapi_spec", "frontend_spec", "test_plan"]
        if not state.get(k)
    ]
    if missing:
        raise RuntimeError(f"Parallel agents incomplete: {missing}")

    return state  # pass through to reviewer_agent

Full Request-to-Output Flow

1
POST /projects
User submits "Build a subscription tracking app". FastAPI creates a project row in PostgreSQL, assigns a project_id, and queues a Celery task. Returns project_id immediately — doesn't wait for agents.
2
Celery runs PM Agent
Worker picks up the task. LangGraph starts the graph with thread_id = project_id. PM Agent runs, writes requirements to state. State is saved to PostgreSQL.
state["requirements"] = "..."
3
Graph pauses at Gate 1
LangGraph hits interrupt_before=["architect_agent"]. Saves full state to PostgreSQL. Celery task completes. Project status in DB: awaiting_gate1.
4
GET /projects/:id (client polls)
Frontend reads project status and the requirements text from DB. User reviews the requirements document in the UI. Can add notes or edits.
5
POST /projects/:id/approve (Gate 1)
FastAPI calls workflow.update_state() to inject gate1_approved=True and any user feedback. Queues a new Celery task to resume.
6
Celery resumes — Architect Agent runs
Graph resumes from the checkpoint. Architect Agent reads state["requirements"] and any gate feedback. Writes architecture, schema, and API surface to state. Graph pauses again at Gate 2.
7
Gate 2 approval — parallel agents fire
After user approves architecture, graph dispatches Backend + Frontend + QA agents in parallel via Send(). All three Celery sub-tasks run concurrently. Each writes its output to state.
Send("backend_agent", state) · Send("frontend_agent", state) · Send("qa_agent", state)
8
Join → Reviewer Agent → END
Once all three parallel agents complete, the join node validates their outputs. Reviewer Agent reads everything, produces the review report and quality score. Graph reaches END.
9
Final package assembled
FastAPI reads the final state from the LangGraph checkpoint. Writes each field to a file (requirements.md, openapi.yaml, etc.). Writes the metrics to the observability table. Marks project complete. User downloads the bundle.

How Each Agent Knows What To Do

Prompts are built dynamically from state. Downstream agents get richer context because more of state is filled in by the time they run.

PM Agent prompt uses:
state["user_input"]
state["past_decisions"]
state["user_preferences"]
Architect Agent prompt uses:
state["requirements"]
state["gate1_feedback"]
Backend Agent prompt uses:
state["requirements"]
state["architecture"]
state["db_schema"]
state["gate2_feedback"]
Reviewer Agent prompt uses:
state["requirements"]
state["architecture"]
state["db_schema"]
state["openapi_spec"]
state["frontend_spec"]
state["test_plan"]

This is the real value of shared state: By the time the Reviewer runs, the state object contains every prior agent's output. The Reviewer's prompt is essentially the entire project specification in one call. No manual plumbing between agents needed.
